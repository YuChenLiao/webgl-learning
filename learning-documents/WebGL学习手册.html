1认识 WebGL

WebGL 是浏览器里的一套底层图形绘制 API，它做的事情只有一件：把顶点数据交给 GPU，让 GPU 按你写的着色器程序画出图元（点、线、三角形）。它没有场景、没有相机、没有光照、没有模型格式，这些概念全都要么你自己实现，要么交给 three.js 这类库。

一句话定位：WebGL 是 GPU 的遥控器，three.js 是坐在遥控器前面的导演。

顶点（Vertex）是什么：可以理解为"三维空间里的一个点"，但它不只是坐标。一个顶点通常打包了它自己的全部信息：位置（x, y, z）、法线（这个点朝向哪边）、UV（贴在纹理的哪个位置）、可能还有颜色、骨骼权重等。你写代码时面对的就是"一长串顶点数据 + 一段处理它们的程序"。

图元（Primitive）是什么：由若干顶点组成的、GPU 能直接绘制的最小单位，只有三种：点、线段、三角形。

为什么 GPU 画图快：CPU 是几个核心在轮流处理任务，GPU 则是成百上千个小核心同时干活。你写的着色器程序会被同时应用于成千上万个顶点——它们之间互不依赖，正好适合并行。这也是为什么图形编程总在强调"把计算搬到 GPU 上"：CPU 算一万次和 GPU 算一万次，不是同一个量级的事。

它处在什么位置

技术抽象层级能做什么不适合
CSS 3D / transform最高给 DOM 元素加平面变换真三维模型、自定义光照
SVG / Canvas 2D高矢量图形、二维图表大规模三维绘制（CPU 光栅化，几万个图元就卡）
WebGL低任意 GPU 绘制：三维场景、粒子、图像处理、通用计算想快速出效果（一切都要手写）
three.js / Babylon.js中场景图、材质、光照、加载器、后处理一应俱全极端定制（需要绕过库的设计）
WebGPU低（更新）WebGL 的继任者：显式计算、渲染管线对象、计算着色器老设备与旧浏览器兼容

WebGL 2 相比 1 带来的实用能力：顶点数组对象（VAO）成为核心特性、实例化渲染（drawArraysInstanced）、多渲染目标（MRT）、统一缓冲（UBO）、更多的纹理格式与 3D 纹理、GLSL ES 3.00（in/out 语法、非方阵矩阵、整数运算）。其中 VAO 与实例化是写现代渲染代码的刚需，WebGL 1 里靠扩展才有，且体验割裂。

WebGL 1 还要不要了解？只需要知道差异，用于看懂老代码。核心差别：GLSL 版本（attribute/varying vs in/out）、gl_FragColor vs 自定义 out 变量、纹理非 2 次幂的限制、VAO 需要 OES_vertex_array_object 扩展。本文全部使用 WebGL 2 写法。

WebGPU 会不会取代它

会，但时间尺度比想象中长。当前状态（2026 年）：

浏览器WebGPU 支持备注

Safari / iOS Safari26.0+（2025）需较新的系统版本

结论：WebGPU 已经可用，但 WebGL 2 仍是覆盖最广的选择。真实项目里的通行策略是"先写 WebGL 2，把渲染抽象层做薄，条件允许时切到 WebGPU"。three.js 从 r160 之后就把 WebGPU 做成了独立入口（three/webgpu），同一套场景代码可以切换渲染器，正是这个思路。

为什么一切都是三角形：三维模型无论多复杂，最终都会被切成三角形。三个原因：① 三点必定共面，不会出现"四点不共面"这种麻烦；② 三角形是最简单的多边形，光栅化算法最省事；③ 市面上的显卡硬件就是为三角形优化的。所以你在建模软件里看到的"曲面"，本质是成千上万个三角形拼出来的近似。

面数（多边形数量）：指的通常就是三角形数量。手机上一个精细模型可能 5 万–20 万个三角形，游戏角色几十万，而每帧要画的三角形总数最好控制在百万级以内——这是性能预算的基本单位。

着色器（Shader）：跑在 GPU 上的两段小程序，用类 C 的语言（GLSL）编写。一段管顶点（顶点着色器），一段管像素颜色（片元着色器）。它们不是"调用一次执行一次"的普通函数，而是被 GPU 同时跑几十万遍——这是图形编程最需要建立的心智模型。

两个着色器是整个 WebGL 编程的核心。你在 JS 里做的所有事（创建缓冲、上传纹理、设置 uniform）都是为这两段小程序准备输入。调试 WebGL 问题，九成时间应该花在"顶点数据对不对"和"着色器算得对不对"上。

什么时候该用原生 WebGL

用 three.js

常规三维展示、模型查看、数据可视化、产品配置器。库帮你处理了矩阵、光照、材质、加载器，开发效率差一个数量级。

用原生 WebGL

包体积敏感（three.js 压缩后仍有数百 KB）、需要极致控制（自定义渲染管线）、做通用计算（GPGPU）、要理解原理以便修改库的行为。

两者结合

最常见：three.js 搭场景，遇到性能瓶颈或特殊效果时用 ShaderMaterial / onBeforeCompile 注入自定义 GLSL。这就需要你能读懂原生 WebGL。

// CSS 的 width/height 只决定显示尺寸。两者不一致就会模糊。
function resize(canvas) {
  const dpr = Math.min(window.devicePixelRatio || 1, 2);   // 限制到 2，避免 4K 屏渲染压力过大
  const w = Math.floor(canvas.clientWidth * dpr);
  const h = Math.floor(canvas.clientHeight * dpr);
  if (canvas.width !== w || canvas.height !== h) {
    canvas.width = w;
    canvas.height = h;
  }
  return dpr;
}

2.4 工程化建议

  • 着色器用模板字符串或独立文件：放在 JS 里便于构建期不做额外处理；放进单独文件则需要构建插件或运行时 fetch。

GLSL 文件的后缀是什么：没有官方标准。GLSL 规范（包括 GLSL ES 3.00）只定义语言本身，不规定文件扩展名——因为着色器的原生用法是把源码作为字符串传给 glShaderSource()，语言层面根本没有"文件"这个概念。后缀是社区和工具链约定出来的，作用只有两个：给人看、给工具识别。

约定俗成的后缀：

后缀含义WebGL 是否支持
.glsl通用，不分阶段是（最常见的选择）
.vert / .vs顶点着色器（vertex）是
.frag / .fs片元着色器（fragment）是
.geom / .gs几何着色器否（桌面 GLSL 专属）
.tesc / .tese细分控制 / 细分求值着色器否
.comp / .cs计算着色器否（需 WebGPU）
.wgslWebGPU 的着色器语言否（不是 GLSL，是另一种语言）

前端项目里的三种实际做法：

  1. 写在 JS 模板字符串里（three.js 官方示例库的做法）。它的 examples/jsm/shaders/ 目录下全都是 .js 文件，以字符串形式导出着色器，没有一个 .glsl 文件。优点是没有构建配置负担，缺点是编辑器里没有语法高亮。
  2. 独立文件 + 打包插件：Vite 用 vite-plugin-glsl（默认识别 .glsl、.wgsl、.vert、.frag、.vs、.fs），Webpack 用 raw-loader 或 glslify-loader。这样才有语法高亮与 #include 复用能力。
  3. 运行时 fetch：把 .glsl 当普通文本文件请求回来。不推荐——多一次网络往返，且要自己处理加载顺序。

两个提醒：#include 是工具提供的能力，不是 GLSL 语法，原生 WebGL 不支持，必须靠 glslify 或 vite-plugin-glsl 这类工具在构建期做文本替换；另外浏览器并不认识 .glsl 后缀，直接 <script src="x.glsl"> 会因为 MIME 类型不对而失败，必须经由上面的第 1 或第 2 种方式。

  • 封装三层：Program（编译链接 + uniform 缓存）、Buffer（数据上传 + VAO 绑定）、Renderer（绘制流程）。第五节的案例就是按这个分层写的。
  • 类型提示：TypeScript 内置 lib.dom 已包含 WebGL2RenderingContext 的完整类型，写 TS 时不需要额外装包。
  • 资源释放：deleteBuffer / deleteTexture / deleteProgram 必须手动调用。WebGL 对象不受 JS 垃圾回收自动管理，热更新或频繁创建时会泄漏显存。

如何引用 GLSL 文件

目标只有一个：把着色器源码取到 JS 里变成字符串，因为它最终要交给 gl.shaderSource(shader, source)（或 three.js 的 ShaderMaterial 的 vertexShader / fragmentShader 字段）。不同构建环境下写法不同：

环境做法是否支持 #include
Viteimport src from './x.vert?raw'（内置能力，零依赖）否
Vite + 插件装 vite-plugin-glsl，直接 import src from './x.vert'是
Webpack 5配置 type: 'asset/source'，然后正常 import否（需 loader）
无构建工具fetch 取文本，或用内联 <script> 标签否
js方案一：Vite 的内置 ?raw（最简单，无需任何插件）
// 任何文件加上 ?raw 后缀，Vite 都会把它当纯文本导入
import vertexSource from './shaders/main.vert?raw';
import fragmentSource from './shaders/main.frag?raw';

const vs = gl.createShader(gl.VERTEX_SHADER);
gl.shaderSource(vs, vertexSource);
gl.compileShader(vs);

// TypeScript 不需要额外声明：Vite 自带的 vite/client 类型已包含 *?raw
// 前提是 tsconfig.json 里有 "types": ["vite/client"]
js方案二：vite-plugin-glsl（需要 #include 复用时用它）
// ① 安装：pnpm add -D vite-plugin-glsl
// ② vite.config.js
import { defineConfig } from 'vite';
import glsl from 'vite-plugin-glsl';

export default defineConfig({
  plugins: [glsl()],          // 默认识别 .glsl / .vert / .frag / .vs / .fs / .wgsl
});

// ③ 之后直接 import，无需 ?raw 后缀
import vertexSource from './shaders/main.vert';
import fragmentSource from './shaders/main.frag';

// ④ TypeScript 项目需要加类型声明，否则会报"找不到模块"
// tsconfig.json: "compilerOptions": { "types": ["vite-plugin-glsl/ext"] }
// 或在某个 d.ts 里写：/// <reference types="vite-plugin-glsl/ext" />

// ⑤ #include 的用法（构建期做文本替换，不是 GLSL 语法）
// main.frag:
//   #include chunk0.frag;
//   void main() { ... }
// include 的路径相对于当前文件，也可以用 root: '/' 配置根目录
js方案三：Webpack 5 与无构建环境
// ---------- Webpack 5：用内置的 asset/source，不必装 raw-loader ----------
// webpack.config.js
module.exports = {
  module: {
    rules: [
      { test: /\.(glsl|vert|frag|vs|fs)$/, type: 'asset/source' },
    ],
  },
};
// 之后正常 import，得到的就是字符串
import fragmentSource from './shaders/main.frag';

// ---------- 无构建工具：内联 script 标签（传统做法，浏览器不会执行它）----------
// <script id="vs" type="x-shader/x-vertex">
//   #version 300 es
//   in vec3 aPosition;
//   void main() { gl_Position = vec4(aPosition, 1.0); }
// </script>
const source = document.getElementById('vs').textContent;

// ---------- 无构建工具：fetch 取文本（要求 http 协议，file:// 会被拦）----------
const res = await fetch('./shaders/main.vert');
const vertexSource = await res.text();
怎么选：只想要字符串、不想加依赖 → Vite 的 ?raw；着色器会被多个材质复用、需要 #include 拆分公共函数 → vite-plugin-glsl；用 Webpack → asset/source 一行配置搞定；跟着本手册的案例练手（单文件 HTML）→ 直接写模板字符串最省事。
另一个惯例值得知道：three.js 官方示例库把着色器写成 .js 文件导出字符串（examples/jsm/shaders/ 目录下全是这种），完全没有 .glsl 文件——因为这样不需要任何构建配置，缺点是编辑器里没有语法高亮。

4核心概念详解

4.1 渲染管线：每个阶段在做什么

① 顶点着色器：把顶点搬到正确的位置

输入的每个顶点都独立执行一次，所以它不能访问其他顶点，也不能创建或销毁顶点。它必须做两件事：

  • 算出 gl_Position：顶点在裁剪空间的齐次坐标，这是唯一强制的输出。
  • 把后续片元阶段需要的数据（UV、法线、颜色、世界坐标）通过 out 变量传下去，它们在光栅化时会按重心坐标插值。

可用的输入有三类：

类型声明更新频率典型用途
顶点属性in vec3 aPosition;每顶点一次位置、法线、UV、切线、颜色、骨骼权重
Uniformuniform mat4 uMvpMatrix;每次绘制调用内保持不变MVP 矩阵、光照参数、时间、纹理采样器
纹理uniform sampler2D uTex;—采样贴图（顶点着色器里也能采样）

插值（Interpolation）是什么：顶点着色器只处理"顶点"，但屏幕上真正上色的是顶点之间的无数个像素。GPU 会自动把顶点上的数据（颜色、UV、法线）按距离比例混合到中间的每个像素上，这个过程就是插值。

它具体怎么算：重心坐标。三角形内任意一点都能表示成三个顶点的加权组合，三个权重之和为 1，这组权重就叫重心坐标。顶点上传下来的属性就按它加权平均。

举个具体的：三个顶点分别是红、绿、蓝，某点的重心坐标是 (0.5, 0.3, 0.2)，它的颜色就是 0.5×红 + 0.3×绿 + 0.2×蓝。落在顶点上是 (1,0,0) 得到纯红，落在三角形正中是 (1/3,1/3,1/3) 得到三者平均。一个三角形三个顶点给不同颜色，中间能平滑渐变，就是这个机制。

一个重要结论：三角形内部不会产生新顶点，只产生片元。GPU 不会把三角形切得更细，它只为覆盖到的每个像素生成一个片元。所以片元着色器里拿不到"这是内部第几个点"这类信息，因为内部点根本不存在。

另外 GPU 默认做的是透视校正插值（用 1/w 加权）。若按屏幕空间直接线性插值，斜视地面时纹理会明显扭曲拉伸，硬件默认修正了这一点，你不需要手动处理，但理解它能解释"远处纹理挤压变形"这类现象。

由此可以想明白一件事：顶点着色器算出的结果在中间是"过渡"出来的，不是重新算的。逐顶点光照在低模上显得假，正是因为高光位置是三个顶点的光照结果插值而来，而真实高光可能恰好落在三角形中间，插值表现不出来。

两个着色器都不"负责绘制"：这是新手最容易建立错误心智模型的地方。它们只是流水线上两个可编程的计算阶段，真正把图元变成屏幕像素的是中间那些固定管线（光栅化）与之后的逐片元操作。把"计算"和"绘制"分开看，后面的性能分析才有落脚点。

常见误解对照：

听起来合理的说法实际情况
顶点着色器绘制顶点和边界它只计算顶点位置（输出 gl_Position），不绘制任何东西；"边界"更不是它的职责
片元着色器绘制颜色和纹理它计算每个像素的颜色；纹理只是数据来源之一（顶点着色器同样能采样纹理），写进帧缓冲是后面的固定阶段
顶点着色器的输出直接给片元着色器中间隔着光栅化与插值：3 个顶点的数据被插值到几万个片元上，这一步才是两个着色器的桥梁

准确的一句话分工：顶点着色器决定"这个顶点到屏幕的哪里"，片元着色器决定"这个像素是什么颜色"，中间由固定管线负责把前者的输出插值给后者。想改变形状就去动顶点着色器（顶点位移做旗帜飘动、水面起伏），想改变表面细节就去动片元着色器（光照、纹理、程序化图案）。

② 图元装配与裁剪

顶点着色器输出的是一个个孤立的顶点，装配阶段按 drawArrays(mode, ...) 的 mode 把它们连成图元：

mode含义顶点消耗
gl.POINTS独立点1
gl.LINES独立线段2
gl.LINE_STRIP连续折线n（复用前一个点）
gl.TRIANGLES独立三角形（最常用）3
gl.TRIANGLE_STRIP三角带n（每 3 个连续点成一个三角形，绕序交替）
gl.TRIANGLE_FAN三角扇（共用起点）n（适合凸多边形）

GPU 本质上只会画三角形，任何曲面都要先三角化。模型的"面数"指的就是三角形数量。

光栅化（Rasterization）：把"数学上无限精确的三角形"转换成"屏幕上一个个离散的像素"的过程。因为屏幕是由有限的小方块组成的，这个转换本身就是一种近似——这也是后面会讲的锯齿（走样）问题的根源。

片元（Fragment）与像素（Pixel）的区别：片元是"候选像素"，它带着自己的位置、颜色、深度等信息，但还没确定能不能显示。要经过深度测试、混合等一系列检查之后，通过检查的片元才会真正写成像素。分清这两个词，很多文档读起来就顺了。

③ 光栅化与片元着色器

光栅化把三角形覆盖到的像素位置生成"片元"（fragment，可理解为候选像素），片元着色器对每个片元执行一次并输出一个颜色。它比顶点着色器执行次数多得多：一个覆盖 10 万个像素的三角形，顶点只有 3 个，片元却有 10 万个。所以性能瓶颈通常在片元阶段。

由此推出的取舍：把光照计算放在顶点着色器（Gouraud 逐顶点光照）比放在片元着色器（Phong 逐像素光照）便宜得多，但结果要靠插值得到，高光在低模上会明显失真。这是画质与性能的经典权衡。

④ 逐片元操作：这个像素最终能不能显示、显示成什么

剪裁测试 →模板测试 →深度测试 →混合 →写入帧缓冲
  • 剪裁测试：gl.scissor 限制绘制矩形区域，常用于局部刷新。
  • 模板测试：用模板缓冲做遮罩，实现镜面、描边、阴影体积。
  • 深度测试：判断片元是否被更近的物体挡住。
  • 混合：把新片元与帧缓冲已有颜色按公式合成，实现透明与发光。

坐标系的手性：三维坐标系分左手系与右手系，区别在 Z 轴的方向。

  • 左手系：DirectX 与部分建模软件用左手系。

为什么要有这么多坐标系：每一步都只解决一件事。模型空间方便建模（原点在物体自身中心），世界空间方便摆放（统一参考系），相机空间方便投影（把相机挪到原点、朝向固定），裁剪空间方便 GPU 判断可见性。这种"分层"的设计模式在渲染里反复出现。

4.3 着色器与 GLSL ES 3.00

GLSL 是什么语言：一种类 C 的着色器语言，语法上与 JS 有几点重要差别：

  • 强类型、无隐式转换：1.0 + 1 在 JS 里没问题，在 GLSL 里是错误，必须写成 1.0 + 1.0。整数与浮点数是两套完全不同的类型。
  • 原生支持向量与矩阵：vec3、vec4、mat4 是内置类型，可以整体做加减乘除，还能按分量组合（v.xy、v.xyz、vec3(v.rg, 0.0)）。这种"分量访问"是 GLSL 写起来最舒服的地方。
  • 没有字符串、没有对象、没有闭包：它只做数学计算。
  • 调试手段有限：没有断点，最常用的办法是把中间值转成颜色输出到屏幕上"看一眼"。
js编译与链接：把错误信息变成可定位的报错
export function compileShader(gl, type, source) {
  const shader = gl.createShader(type);
  gl.shaderSource(shader, source);
  gl.compileShader(shader);

  if (!gl.getShaderParameter(shader, gl.COMPILE_STATUS)) {
    const log = gl.getShaderInfoLog(shader);
    const kind = type === gl.VERTEX_SHADER ? '顶点' : '片元';
    gl.deleteShader(shader);
    // 把源码带行号打印出来：报错里的行号对应的是这段字符串，不是你的 JS 文件
    const numbered = source.split('\n')
      .map((line, i) => `${String(i + 1).padStart(3)} | ${line}`).join('\n');
    throw new Error(`${kind}着色器编译失败:\n${log}\n---- 源码 ----\n${numbered}`);
  }
  return shader;
}

export function createProgram(gl, vertexSrc, fragmentSrc) {
  const vs = compileShader(gl, gl.VERTEX_SHADER, vertexSrc);
  const fs = compileShader(gl, gl.FRAGMENT_SHADER, fragmentSrc);

  const program = gl.createProgram();
  gl.attachShader(program, vs);
  gl.attachShader(program, fs);
  gl.linkProgram(program);

  // 链接完成后 shader 对象已完成使命：program 已独立持有编译结果
  // 注意这行只是"打删除标记"，不会立即释放（因为 shader 仍附着在 program 上）
  gl.deleteShader(vs);
  gl.deleteShader(fs);

  if (!gl.getProgramParameter(program, gl.LINK_STATUS)) {
    const log = gl.getProgramInfoLog(program);
    gl.deleteProgram(program);
    throw new Error('程序链接失败: ' + log);
  }

  // 一次性取出所有活跃 uniform 的位置，避免每帧查询
  const uniforms = {};
  const uCount = gl.getProgramParameter(program, gl.ACTIVE_UNIFORMS);
  for (let i = 0; i < uCount; i++) {
    const info = gl.getActiveUniform(program, i);
    const name = info.name.replace(/\[0\]$/, '');   // 数组 uniform 会带 [0]
    uniforms[name] = gl.getUniformLocation(program, info.name);
  }

  // 取出活跃顶点属性，用于按名字绑定 VBO
  const attribs = {};
  const aCount = gl.getProgramParameter(program, gl.ACTIVE_ATTRIBUTES);
  for (let i = 0; i < aCount; i++) {
    const info = gl.getActiveAttrib(program, i);
    attribs[info.name] = gl.getAttribLocation(program, info.name);
  }

  return { program, uniforms, attribs };
}

/**

 * GL 的规则是"引用计数 + 延迟删除"——只要 shader 还附着在 program 上，
 * deleteShader 就只是给它打个删除标记，真正销毁发生在 program 被删除时。
 * 想在链接后立刻释放，必须先 detachShader 再 deleteShader（让引用归零）。

in vec3 aPosition;
in vec3 aNormal;
in vec2 aUv;

uniform mat4 uModelMatrix;
uniform mat4 uViewProjectionMatrix;
uniform mat3 uNormalMatrix;        // = 模型矩阵左上 3x3 的逆转置

out vec3 vWorldPos;
out vec3 vNormal;
out vec2 vUv;

void main() {
  vec4 worldPos = uModelMatrix * vec4(aPosition, 1.0);
  vWorldPos = worldPos.xyz;
  vNormal = uNormalMatrix * aNormal;
  vUv = aUv;
  gl_Position = uViewProjectionMatrix * worldPos;
  gl_PointSize = 2.0;              // 仅当绘制 POINTS 时有意义
}

// ============ 片元着色器 ============
#version 300 es
precision highp float;             // 片元着色器没有默认精度，必须显式声明

in vec3 vWorldPos;
in vec3 vNormal;
in vec2 vUv;

uniform sampler2D uBaseMap;
uniform vec3 uLightPos;
uniform vec3 uCameraPos;

out vec4 outColor;                 // WebGL1 里用的是内置的 gl_FragColor

void main() {
  vec3 base = texture(uBaseMap, vUv).rgb;    // WebGL1 里是 texture2D()

  vec3 N = normalize(vNormal);
  vec3 L = normalize(uLightPos - vWorldPos);

  float diff = max(dot(N, L), 0.0);          // Lambert 漫反射

  vec3 V = normalize(uCameraPos - vWorldPos); // Blinn-Phong 高光（半程向量，比反射向量便宜）
  vec3 H = normalize(L + V);
  float spec = pow(max(dot(N, H), 0.0), 64.0);

  vec3 color = base * (0.15 + 0.85 * diff) + vec3(spec);

  outColor = vec4(pow(color, vec3(1.0 / 2.2)), 1.0);   // 线性空间算完光照，再转 sRGB 输出
}

precision 精度限定符为什么存在：GPU 是高度并行的硬件，浮点数的位数越多，单个核心占用的面积与功耗就越大。移动 GPU 为了控制发热，故意提供了较低精度的浮点类型：

  • highp：高精度（约 32 位），坐标计算必须用它。
  • mediump：中精度（通常 16 位），颜色、UV、法线够用。
  • lowp：低精度（8 位左右），只适合简单的 0~1 系数。

片元着色器必须显式声明精度（如 precision mediump float;），顶点着色器有默认值。写移动端时把能降的降到 mediump 是常见的性能优化，但坐标与深度相关计算必须留在 highp，否则会出现物体抖动。

别硬编码 attribute location：上面写 0/1/2 只是为便于阅读。生产代码要么用 gl.getAttribLocation(program, 'aPosition') 动态查询，要么在链接前用 gl.bindAttribLocation(program, 0, 'aPosition') 显式绑定，让 location 稳定可控。后者是引擎里的常见做法。

属性数量由谁决定：是双向约定，不是单方面。着色器决定"我要哪些输入"，CPU 侧决定"这些输入从哪来、怎么读"，两边必须一一对应。

着色器里写 in vec3 aPosition; 只是声明需求，GPU 并不知道数据在哪。CPU 侧必须用 vertexAttribPointer(location, 分量数, 类型, 归一化, 步长, 偏移) 加 enableVertexAttribArray 把它接到具体缓冲上。声明与配置缺一不可。

两边对不上，后果完全不同：

  • 着色器声明了但没用到（写了 in 却没在 main 里引用）：编译器会把它优化掉，getAttribLocation 返回 -1，此时调 enableVertexAttribArray(-1) 会直接报 INVALID_VALUE。这是"明明都写了却报错"的常见原因。
  • 着色器用了但 CPU 没配置：该属性保持默认值（通常是 (0, 0, 0, 1)），不报错但画面异常。排查时若控制台干净，就往这个方向查。

数量有硬件上限：WebGL 2 规范要求至少支持 16 个顶点属性（MAX_VERTEX_ATTRIBS）。真不够用时，常见做法是把多个小数据打包进一个 vec4（例如用归一化的 UNSIGNED_BYTE 传颜色或骨骼权重），或把数据放进纹理在顶点着色器里采样。

"互不冲突"的准确含义：各属性确实互不覆盖，但在交错布局里它们共享同一个 STRIDE，只是 offset 不同，所以是配套关系而非彼此独立。[x,y,z,u,v] 的 stride 是 20 字节，position 偏移 0、uv 偏移 12；把 uv 改成三分量，stride 和后续偏移全都要跟着改。想让它们真正独立，就把每个属性放进单独的 VBO，那时各自的 stride 才互不相干（通常等于分量数 × 4）。

最本质的一点：WebGL 不关心也不理解这些数字的语义。它只知道"某号属性是 3 个 float、从第 0 字节开始、每 20 字节取一组"。这串数字是位置、是法线、还是"每个顶点的风力强度"，完全由你的着色器命名与使用方式决定。名字是你起的，含义是你赋予的，这也是为什么你可以自由添加自定义属性。

这些属性的分工有什么不同：属性列表看起来只是一串数字，但它们的"角色"差别很大，理解这个差别能省掉很多困惑。

属性角色谁消费它影响形状吗
position决定几何形状顶点着色器算出 gl_Position，交给光栅化器是，唯一影响轮廓的属性
color结果本身片元着色器直接当颜色用否
uv查表用的坐标片元着色器拿去做 texture() 采样否
normal参与光照计算的方向片元着色器算点积时用否

三句话概括：position 决定形状；color 是终点（插值完就是最终颜色）；uv 与 normal 是参数（还要再参与一次运算才有意义）。uv 里的 0.3、0.7 本身没有任何颜色含义，必须查一次纹理才换成颜色，所以 uv 出错时表现为"图案位置不对"而不是"颜色不对"。

数据流向也不一样：position 在顶点着色器里就被消费掉了（变成 gl_Position），不参与后续传递；而 color、uv、normal 要通过顶点着色器的 out 传到片元着色器的 in，靠光栅化插值铺满整个三角形。

但它们遵循同一套机制：每顶点一份数据 → 光栅化时插值 → 片元着色器使用。区别只在"表达什么含义"和"片元着色器拿它做什么"。理解了这条机制，以后新增任何属性都只是照葫芦画瓢。

属性列表是自由的：L1 用 6 个 float（位置 + 颜色），L2 用 5 个（位置 + UV），L3 的球体用 8 个（位置 + 法线 + UV）。你还能加自定义属性，比如每个顶点的摆动相位、风力权重。只要 CPU 侧的 vertexAttribPointer 与着色器里的 in 声明对得上，加几个都行。STRIDE 与偏移量就是这套约定的具体数字。

一个两分钟就能做的实验：把片元着色器的输出改成 outColor = vec4(vUv, 0.0, 1.0);，也就是把 UV 当颜色显示。你会看到红色横向渐变、绿色纵向渐变的图案，四个角分别是黑、红、黄、绿。这就是 UV 在模型表面的实际分布，能帮你建立"UV 是贴在表面上的二维坐标系"这个直觉，调试纹理问题时常年管用。

Usage 提示含义场景

DYNAMIC_DRAW会反复修改每帧变化的顶点（CPU 计算的粒子）

4.5 矩阵与空间变换

矩阵是什么：在图形学里，矩阵就是"一次空间变换的数学表示"。一个 4×4 矩阵乘上一个顶点坐标，就得到变换后的新坐标。旋转、缩放、平移、投影，全都能表示成矩阵——这样 GPU 只需要做同一件事（矩阵乘法），而不必关心你想要的到底是哪种变换，硬件因此高度统一且高效。

矩阵乘法为什么不能交换顺序：因为矩阵乘法表示"依次施加变换"。旋转 × 平移 表示"先平移再旋转"，而 平移 × 旋转 表示"先旋转再平移"——结果完全不同。这一点在写 MVP 时至关重要：P × V × M × 顶点，是从右往左依次施加。

为什么要自己算矩阵：虽然 three.js 会把这一步封装掉，但当你遇到"物体位置对不上""旋转轴不对""缩放后变形"这类问题时，能看懂矩阵是唯一能真正定位问题的方式。

为什么是 4x4 矩阵

三维变换需要平移，3x3 矩阵只能表达线性变换（旋转、缩放、错切），无法表达平移。引入第四个分量后平移成为矩阵乘法的一部分，同时提供了透视除法所需的 w。这就是齐次坐标：点写作 (x, y, z, 1)，方向向量写作 (x, y, z, 0)——后者的 w=0 使它不受平移影响，正是"方向不该被平移"的数学表达。

矩阵变换的顺序：代码顺序与顶点经历的顺序是相反的。这是学 WebGL 时最容易卡住的一处，值得单独讲清。

矩阵乘法链 A × B × C × v 的含义是：先对 v 做 C，再做 B，最后做 A。也就是说要从右往左读。而代码是自上而下写的，每写一行都在往右边追加一个矩阵：

js代码顺序 vs 顶点经历的顺序
mat4.identity(model);                        // M = I
mat4.translate(model, model, [0, 0, -4]);    // M = I × T        = T
mat4.rotateY(model, model, angle);           // M = T × Ry
mat4.scale(model, model, [2, 2, 2]);         // M = T × Ry × S

// 最终 M = T × Ry × S
// 作用到顶点：v' = T × Ry × S × v
// 从右往左读 → 顶点依次经历：S（缩放）→ Ry（自转）→ T（平移）

所以"代码里写在最下面的那一行，反而最先作用于顶点"。记住这一句，绝大多数顺序问题都能自己推出来。

为什么顺序不能随便换：矩阵乘法不满足交换律，T × R 与 R × T 是两个完全不同的变换：

  • T × R（顶点先旋转再平移）：物体在原地转好后，被搬到目标位置。这是我们想要的"自转"。
  • R × T（顶点先平移再旋转）：物体先被搬到那个位置，然后绕着世界原点转动。结果是"公转"，物体会飞出去转圈。

生活类比：就像布置展台，应该先在原地把展品摆好姿势（缩放、旋转），最后再搬到展台上（平移）。反过来先搬到展台再旋转，展品就会绕着展厅中心甩出去。

验证方法：把旋转角固定成一个不变的值（比如 0.5），两种顺序各跑一次。正确顺序下物体会在画面中央原地倾斜，错误顺序下它会跑到画面一侧甚至转到相机背后消失。

js组装 MVP（注意顺序：从局部一路推到裁剪空间）
import { mat3, mat4 } from 'gl-matrix';

// 重要：代码是从上往下写，但顶点是从下往上被作用的
// 下面三行的实际效果是：先缩放、再绕 Y 轴自转、最后平移到世界位置

mat4.rotateY(model, model, performance.now() / 1000);  // 中间作用：绕自身 Y 轴自转
mat4.scale(model, model, [0.5, 0.5, 0.5]);             // 最先作用：缩放
// 为什么这个顺序对：矩阵链是 T × Ry × S，从右往左作用到顶点，
// 即"先缩放、再旋转、最后平移"——这是物体变换的标准顺序。
// 反过来写（先 rotate 后 translate）会让物体绕世界原点公转，而不是自转。

// 非等比缩放会让法线不再垂直于表面，正确做法是取模型矩阵左上 3x3 的逆转置
const normalMatrix = mat3.create();
mat3.normalFromMat4(normalMatrix, model);

text透视投影矩阵（OpenGL / WebGL 约定，z ∈ [-1, 1]）
令 f = 1 / tan(fovy / 2)，aspect = 宽 / 高，n = near，far = far

[ f/aspect     0          0                          0                    ]
[    0         f          0                          0                    ]
[    0         0    (far+n)/(n-far)      2*far*n/(n-far)                   ]
[    0         0         -1                          0                    ]

三个关键点：
· 第 4 行是 (0, 0, -1, 0)，把 z 取反写进 w —— 这就是"透视除法"的开关
· 相机前方 z 为负，所以 w = -z 为正；除以 w 后远处被压缩、近处被放大，即近大远小
· aspect 只作用于 x，补偿屏幕宽高比，否则画面会被拉伸

near 不能太小：深度精度是非线性分布的，near 太小会让远处精度严重不足，
表现为"远处表面深度冲突、闪烁"（z-fighting）。经验值 near ≥ 0.1，
且把 far / near 的比值控制在 1000 以内（如 0.1 : 100）。

逆矩阵与转置是什么：

  • 转置：把矩阵的行列互换，记作 Mᵀ，直接换元素位置即可。
  • 逆矩阵：M⁻¹ 是"撤销变换"的矩阵——两者相乘得到单位矩阵（相当于什么都没做）。只有可逆的变换（旋转、平移、非零缩放）才有逆矩阵。

法线矩阵同时用到这两步（先求逆、再转置），直观理解是：表面被拉伸时，法线的变化方向恰好与顶点相反。把球在 Y 轴压扁，顶点的 Y 变小了，但水平朝上的那些法线反而要变得更陡。这就是"不能直接用模型矩阵变换法线"的原因。

正交投影的适用场景

mat4.ortho 没有近大远小，平行线保持平行。用于：2D UI 与图表、工程制图、等距视角（isometric）游戏、阴影贴图渲染（线性深度分布，精度更好）。

变换出问题时的排查法：把三个矩阵拆开单独验证。先只留模型矩阵（视图与投影设为单位矩阵），物体应出现在原点附近；再固定模型、把相机放到 [0,0,5] 看向原点，物体应正确缩小；最后加上投影。逐段排除比盯着黑屏猜快十倍。另一个技巧：把 gl_Position 临时改成 vec4(aPosition, 1.0)，如果这样能看到内容，说明顶点数据没问题，故障在矩阵。

4.6 纹理

UV 坐标是什么：三维模型上的每个顶点"贴在图片的哪个位置"，需要一个二维坐标来描述，这就是 UV。之所以叫 UV 而不是 XY，是为了与三维坐标区分开——U 是横向，V 是纵向。

  • UV 的范围是 0 到 1：(0,0) 是纹理的一个角，(1,1) 是对角。超出这个范围的行为由 wrap 参数决定（重复、拉伸边缘像素等）。
  • 原点位置是历史遗留的坑：WebGL 的纹理坐标原点在左下角，而图片文件的原点在左上角，所以加载图片纹理时常常需要翻转 Y（UNPACK_FLIP_Y_WEBGL）。这是每个做三维的人都会踩一次的坑。

纹素（Texel）与像素：纹理上的采样单位叫纹素。贴图 1000×1000 个纹素，投影到屏幕上可能只占 100×100 个像素，也可能被放大到 2000×2000 个像素——两边数量对不上，所以必须靠过滤（插值）来填补，这就是纹理过滤存在的原因。

js纹理的完整创建流程与参数含义
export function createTexture(gl, image, { srgb = true, flipY = true } = {}) {
  const texture = gl.createTexture();
  gl.bindTexture(gl.TEXTURE_2D, texture);

  // 图片加载完成前先用 1x1 像素占位，避免"纹理不完整"导致的黑色物体
  gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA, 1, 1, 0, gl.RGBA, gl.UNSIGNED_BYTE,
    new Uint8Array([255, 255, 255, 255]));

  // WebGL 的纹理原点在左下，多数图片格式的原点在左上，需要翻转 Y
  gl.pixelStorei(gl.UNPACK_FLIP_Y_WEBGL, flipY);

  // 颜色贴图要按 sRGB 解码到线性空间；法线/粗糙度等数据贴图必须保持线性（srgb = false）
  gl.texImage2D(gl.TEXTURE_2D, 0,
    srgb ? gl.SRGB8_ALPHA8 : gl.RGBA,      // 内部格式
    gl.RGBA, gl.UNSIGNED_BYTE,             // 源格式与类型
    image);

  // 缩小过滤用 mipmap 三线性，放大过滤用线性 —— 这是画质与性能的平衡点
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.LINEAR_MIPMAP_LINEAR);
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.LINEAR);

  // 环绕方式：平铺用 REPEAT，单张铺满用 CLAMP_TO_EDGE（防止边缘出现条纹）
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_WRAP_S, gl.REPEAT);
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_WRAP_T, gl.REPEAT);

  gl.generateMipmap(gl.TEXTURE_2D);        // 生成多级渐远纹理
  gl.bindTexture(gl.TEXTURE_2D, null);
  return texture;
}
过滤方式效果性能适用
NEAREST取最近像素，像素风、硬边最便宜像素艺术、数据可视化精确取值
LINEAR双线性插值，平滑便宜放大时使用（MAG_FILTER 默认思路）
LINEAR_MIPMAP_LINEAR三线性，多级渐变需要 mipmap 内存缩小时的正确选择
NEAREST_MIPMAP_NEAREST最近级 + 最近像素便宜性能优先的远景
只设 MIN_FILTER 忘了 MAG_FILTER，或用了 mipmap 过滤却没调 generateMipmap：纹理会被判定为"不完整"（incomplete），采样结果全黑。而且 WebGL 不会报错，只是安静地画出一片黑。gl.getError() 也查不出来，只能靠经验排查。

图片文件里的颜色是 sRGB 编码的（人眼友好的非线性），而光照计算必须在线性空间进行。两者混用会导致画面整体发灰或过曝。规则很简单：

  • 颜色类贴图（漫反射、自发光）→ 用 SRGB8_ALPHA8 内部格式，让 GPU 在采样时自动解码到线性。
  • 数据类贴图（法线、粗糙度、金属度、AO）→ 用普通 RGBA，绝不能做 sRGB 转换，否则数值会被破坏。
  • 光照计算完成后，输出前做一次伽马编码（pow(color, 1/2.2)），或在创建上下文时用 drawingBufferColorSpace 交给浏览器处理。

4.7 光照与法线

法线是什么：垂直于表面、长度为 1 的方向向量，表示"这个表面朝向哪边"。它不表示位置，只表示方向。光照计算的第一步永远是"知道表面朝哪儿"，所以法线错了，任何光照模型都会算错。

点积（Dot Product）的几何意义：两个单位向量的点积等于它们夹角的余弦值 cos θ。这一条是整个光照计算的基础：

  • 法线与光线方向夹角为 0（正对着光）→ dot = 1 → 最亮。
  • 夹角 90 度（与光垂直）→ dot = 0 → 无光。
  • 夹角大于 90 度（背对光）→ dot < 0 → 临床上取 max(dot, 0) 直接按 0 处理。

为什么必须归一化：只有单位向量的点积才等于余弦值。着色器里的 vNormal 经过插值后长度会变，所以每次用之前都要 normalize()——这是新手最常漏的一步，症状是高光忽明忽暗、亮度不合理。

光照的质量取决于三件事：法线是否正确、在哪个空间计算、用什么模型。法线错了，再好的光照模型都是错的。

geometry.computeVertexNormals();

// 自定义几何体的法线推导：三角形两条边的叉积
function faceNormal(a, b, c) {
  const ux = b[0] - a[0], uy = b[1] - a[1], uz = b[2] - a[2];
  const vx = c[0] - a[0], vy = c[1] - a[1], vz = c[2] - a[2];
  // 叉积顺序决定法线朝向，必须与顶点绕序一致（逆时针为正面）
  let nx = uy * vz - uz * vy;
  let ny = uz * vx - ux * vz;
  let nz = ux * vy - uy * vx;
  const len = Math.hypot(nx, ny, nz) || 1;
  return [nx / len, ny / len, nz / len];
}

in vec3 vNormal;
uniform vec3 uLightPos[MAX_LIGHTS];
uniform vec3 uLightColor[MAX_LIGHTS];
uniform float uLightIntensity[MAX_LIGHTS];
uniform vec3 uAmbient;
uniform vec3 uBaseColor;
uniform vec3 uCameraPos;

out vec4 outColor;

void main() {
  vec3 N = normalize(vNormal);
  vec3 V = normalize(uCameraPos - vWorldPos);
  vec3 acc = uAmbient * uBaseColor;              // 环境光作为基础项，避免全黑

  for (int i = 0; i < MAX_LIGHTS; i++) {
    vec3 L = uLightPos[i] - vWorldPos;
    float dist = length(L);
    L /= max(dist, 1e-4);

    // 距离衰减：简单二次衰减，工程上够用且便宜
    float atten = 1.0 / (1.0 + 0.1 * dist + 0.01 * dist * dist);

    float diff = max(dot(N, L), 0.0);
    vec3 H = normalize(L + V);
    float spec = pow(max(dot(N, H), 0.0), 64.0);

    vec3 radiance = uLightColor[i] * uLightIntensity[i] * atten;
    acc += radiance * (uBaseColor * diff + spec);
  }

  outColor = vec4(pow(acc, vec3(1.0 / 2.2)), 1.0);
}

法线贴图与切线空间

法线贴图存的不是世界空间法线，而是切线空间下的扰动方向（RGB 对应 XYZ，平表面为 (0.5, 0.5, 1) 的淡蓝色）。这样做的好处是同一张贴图能用于任意朝向的模型表面。使用时需要构造 TBN 矩阵：

glslTBN 矩阵与法线贴图采样
in vec3 vNormal;
in vec3 vTangent;
in vec3 vBitangent;      // 通常由顶点属性给出，或用 cross(N, T) * handedness 计算
in vec2 vUv;
uniform sampler2D uNormalMap;

vec3 getNormal() {
  vec3 T = normalize(vTangent);
  vec3 N = normalize(vNormal);
  T = normalize(T - N * dot(N, T));      // 施密特正交化，消除累积误差
  vec3 B = cross(N, T);
  mat3 TBN = mat3(T, B, N);

  // 法线贴图是数据贴图：必须是线性空间，且采样后要映射回 [-1, 1]
  vec3 n = texture(uNormalMap, vUv).rgb * 2.0 - 1.0;
  return normalize(TBN * n);
}

4.8 深度、剔除与混合

为什么需要深度缓冲：屏幕上每个像素只能显示一个颜色，可场景里可能有几十个表面投影到同一个像素上，该显示哪个？最早的做法是"画家算法"——把物体按远近排序，从最远开始画，近的覆盖远的。但这个方法有两个致命问题：物体互相穿插时排序无法解决；每次物体变化都要重新排序，成本高。

深度缓冲（Z-Buffer）的做法更聪明：给每个像素额外存一个"当前最近的深度值"，每画一个片元就比一下，更近就覆盖、更远就丢弃。这样一来绘制顺序就无关紧要了，而且几乎不增加成本。这是实时渲染里最重要的发明之一。

绕序为什么能判断正反面：一个三角形投影到屏幕上会变成二维的三个点，按顶点原始顺序连起来，可能是顺时针（CW）也可能是逆时针（CCW）。约定"逆时针为正面"，GPU 就能用极低的成本剔掉背对我们的那些面——大约能省掉一半的片元计算。

绕序与正面判断

一个三角形在屏幕上，顶点按逆时针排列就是正面（默认 CCW）。这不是"朝向相机"，而是投影到屏幕后的二维绕序。所以物体翻面后会出现"看不到内部"的现象——因为内侧的三角形投影后绕序反了，被剔除掉了。调试时如果模型"缺面"，第一件事就是 gl.disable(gl.CULL_FACE) 看看是不是面被剔了。

4.9 帧缓冲与后处理

帧缓冲（Framebuffer）是什么：一块显存区域，装着这一帧要显示的所有数据。它通常包含三部分：颜色缓冲（每个像素的颜色）、深度缓冲（每个像素的深度）、模板缓冲（用于遮罩等特殊效果）。默认情况下 GPU 画进"默认帧缓冲"，也就是屏幕。

帧缓冲对象（FBO）的意义是：你可以自己造一块帧缓冲，让 GPU 画到它里面去，之后把这块内容当成一张纹理来用。这一个能力衍生出了后处理、阴影贴图、镜面反射、屏幕空间效果等大量技术——它们本质都是"先渲染到一个看不见的画布，再拿这个画布做二次加工"。

走样（Aliasing）与抗锯齿：屏幕像素是离散的方格，而几何体边缘是连续的直线或曲线。当一条斜线被塞进方格网格时，只能"整格整格"地近似，边界就会出现阶梯状的锯齿。抗锯齿的思路就是"别只采样一个点"：MSAA 是在每个像素内部取多个采样点求平均；FXAA/SMAA 则是事后分析画面边缘再做模糊。理解了成因，就能明白为什么"抗锯齿一定是有代价的"——它本质上是在用更多采样换更平滑的边界。

帧缓冲对象（FBO）让你把场景渲染到一块纹理而不是屏幕，这是后处理、阴影贴图、镜像反射、拾取等技术的共同基础。

  gl.bindFramebuffer(gl.FRAMEBUFFER, null);
  gl.bindTexture(gl.TEXTURE_2D, null);
  gl.bindRenderbuffer(gl.RENDERBUFFER, null);

阴影贴图：FBO 的经典应用

  1. 从光源视角渲染一遍场景：把相机换成光源的虚拟相机（正交投影用于平行光，透视投影用于点光源），渲染到只带深度附件的 FBO。
  2. 记录每个像素到光源的最近距离：深度纹理由 GPU 自动生成，无需手写着色器逻辑。
  3. 正常渲染场景时比较深度：把当前片元的世界坐标变换到光源空间，比较其深度与阴影贴图中记录的深度。若更远，说明被遮挡，处于阴影中。
  4. 软化阴影边缘：对阴影贴图做多次采样取平均（PCF，Percentage Closer Filtering），消除锯齿。

上下文创建时开启 antialias: true 会启用默认帧缓冲的 MSAA。但离屏渲染不会自动继承 MSAA：WebGL 2 里要创建多重采样的 renderbuffer（renderbufferStorageMultisample）渲染，再用 blitFramebuffer 解析到普通纹理。这也是"加了后处理之后画面边缘变毛糙"的原因，后处理与抗锯齿需要一套专门的处理方案（FXAA / SMAA 是常见替代）。

function screenToWorldRay(mouseX, mouseY, canvas, viewMatrix, projectionMatrix) {
  // ① 屏幕像素 → NDC（注意 y 轴方向相反）
  const ndcX = (mouseX / canvas.clientWidth) * 2 - 1;
  const ndcY = -((mouseY / canvas.clientHeight) * 2 - 1);

  // ② 逆变换矩阵：把 NDC 拉回世界空间
  const invProjection = mat4.invert(mat4.create(), projectionMatrix);
  const invView = mat4.invert(mat4.create(), viewMatrix);

  // ③ 取近平面与远平面上的点（NDC z 分别为 -1 与 1）
  const unproject = (ndcZ) => {
    const v = [ndcX, ndcY, ndcZ, 1];
    // 手动做 invProjection * v（用齐次矩阵乘向量）
    const out = [0, 0, 0, 0];
    for (let row = 0; row < 4; row++) {
      out[row] = invProjection[row] * v[0] + invProjection[4 + row] * v[1]
               + invProjection[8 + row] * v[2] + invProjection[12 + row] * v[3];
    }
    // 透视除法，得到世界空间坐标
    const w = out[3] || 1;
    return [out[0] / w, out[1] / w, out[2] / w];
  };

  const nearWorld = unproject(-1);
  const farWorld = unproject(1);

  // ④ 射线起点取近平面点，方向归一化
  const dir = normalize([farWorld[0] - nearWorld[0], farWorld[1] - nearWorld[1], farWorld[2] - nearWorld[2]]);
  return { origin: nearWorld, direction: dir };
}

function normalize(v) {
  const len = Math.hypot(v[0], v[1], v[2]) || 1;
  return [v[0] / len, v[1] / len, v[2] / len];
}

// ⑤ 射线与球求交（世界空间）
function intersectSphere(ray, center, radius) {
  const oc = [ray.origin[0] - center[0], ray.origin[1] - center[1], ray.origin[2] - center[2]];
  const b = oc[0] * ray.direction[0] + oc[1] * ray.direction[1] + oc[2] * ray.direction[2];
  const c = oc[0] * oc[0] + oc[1] * oc[1] + oc[2] * oc[2] - radius * radius;
  const disc = b * b - c;
  if (disc < 0) return null;               // 无交点
  const t = -b - Math.sqrt(disc);          // 取较近的交点
  return t >= 0 ? t : null;
}

  gl.disable(gl.BLEND);         // 混合会把颜色混脏，必须关
  gl.disable(gl.DITHER);        // 抖动会改变颜色值，也必须关

  gl.clear(gl.COLOR_BUFFER_BIT | gl.DEPTH_BUFFER_BIT);

  gl.useProgram(idProgram);
  for (const obj of objects) {
    gl.uniformMatrix4fv(idUniforms.mvp, false, obj.mvp);
    gl.uniform4fv(idUniforms.idColor, objectIdToColor(obj.id));
    gl.bindVertexArray(obj.vao);
    gl.drawElements(gl.TRIANGLES, obj.indexCount, gl.UNSIGNED_SHORT, 0);
  }
}

// ③ 查询：把鼠标位置换算成帧缓冲像素坐标后读一个像素
function pick(mouseX, mouseY) {
  const dpr = canvas.width / canvas.clientWidth;
  const px = Math.floor(mouseX * dpr);
  const py = idTarget.height - Math.floor(mouseY * dpr);   // WebGL 原点在左下

  const pixel = new Uint8Array(4);
  gl.bindFramebuffer(gl.FRAMEBUFFER, idTarget.framebuffer);
  // readPixels 是同步的，会打断 GPU 流水线：只在点击时调用，别放进动画循环
  gl.readPixels(px, py, 1, 1, gl.RGBA, gl.UNSIGNED_BYTE, pixel);
  gl.bindFramebuffer(gl.FRAMEBUFFER, null);

  const id = pixel[0] | (pixel[1] << 8) | (pixel[2] << 16);
  return id === 0 ? null : id;
}

faces 到 interleaved 的转换在做什么：这段代码是纯粹的数据布局转换，不涉及任何坐标计算。faces 里的 [-S,-S,S] 已经是最终坐标（局部空间坐标），GPU 用的也是同一个数值。转换改变的是"组织方式"：从"按面组织的嵌套数组"变成"GPU 能直接上传的连续内存块"。

产出的两个数组分工明确：

  • interleaved（24 × 5 个 float）：每个顶点 [x, y, z, u, v]，上传给 VBO。
  • indices（36 个）：每面 6 个索引，描述"这些顶点怎么连成三角形"，上传给 EBO。

为什么是 24 个顶点而不是 8 个：这是理解这段代码的关键。立方体只有 8 个角，但每个角被 3 个面共用，而这 3 个面需要的 UV 完全不同（贴图在每个面上的方向不一样），法线也不同。而一个顶点只能携带一组属性。

所以顶点数不是由"几何上有几个位置"决定的，而是由"有多少组不同的位置 + 属性组合"决定的。位置只有 8 个，属性组合有 6 面 × 4 角 = 24 组，于是 24 个顶点。这是图形学里反复出现的原则：位置相同的点，只要属性不同，就必须拆成多个顶点。反过来，这也说明"顶点"这个词容易误导——它不是"空间里的一个点"，而是"一次数据打包"。

隐藏的第三类信息：绕序。每个面里那 4 个点的排列顺序不是随便写的，它决定了三角形的绕序（逆时针为正面），也就决定了开启背面剔除后哪些面可见。顺序写反，整个面会消失。所以这份"人类友好格式"实际编码了三件事：位置、UV 的分配方式、绕序。

这个立方体里 UV 具体怎么工作：前三个数是顶点在三维空间的位置，后两个数是"这个顶点对应图片上的哪个位置"。拿前面那个面举例：

三维坐标UV对应图片的位置
(-S, -S, S)(0, 0)左下角
( S, -S, S)(1, 0)右下角
( S, S, S)(1, 1)右上角
(-S, S, S)(0, 1)左上角

四个角被"钉"在图片的四个角上之后，光栅化会把 UV 连同其他属性一起插值到三角形内部的每个像素：画面正中的像素拿到大约 (0.5, 0.5)，正好取到图片中心；左下角的像素拿到接近 (0.2, 0.2)，取到偏左下的颜色。片元着色器里那句 texture(uTexture, vUv) 就是拿插值后的坐标去图片上取色。所谓"贴图"，本质就是这套坐标映射加上插值，没有别的魔法。

这里也能看出为什么六个面可以用同一套 UV 数组：因为每个面有自己独立的 4 个顶点，[[0,0],[1,0],[1,1],[0,1]] 可以给每个面各用一遍，六面各自完整贴一张图。

两个必须记住的点：① UV 用 0~1 归一化，是为了同一套坐标能配任意分辨率的贴图，换贴图不用改 UV；② WebGL 的 UV 原点在左下角，图片文件的原点在左上角，两者方向相反，所以加载图片纹理时要翻转 Y（UNPACK_FLIP_Y_WEBGL），否则贴图上下颠倒。

立方体的两个经典错误：
① 只给 8 个顶点——每个顶点只能有一组 UV，六面共用同一套坐标，贴图必然错乱；
② 索引绕序写反——开启背面剔除后整个面会消失。遇到"立方体缺面"，先 gl.disable(gl.CULL_FACE) 验证是不是绕序问题。

in vec3 vNormal;
in vec2 vUv;

uniform vec3 uLightColor;
uniform vec3 uCameraPos;
uniform vec3 uAmbientColor;

  vec3 V = normalize(uCameraPos - vWorldPos);
  vec3 H = normalize(L + V);

  float dist = length(uLightPos - vWorldPos);
  float atten = 1.0 / (1.0 + 0.15 * dist + 0.02 * dist * dist);   // 距离衰减

  float diff = max(dot(N, L), 0.0);                  // 漫反射
  float spec = pow(max(dot(N, H), 0.0), 96.0);       // 高光，指数越大越锐
  float rim = pow(1.0 - max(dot(N, V), 0.0), 2.5);   // 边缘光

             + uLightColor * spec * atten * 0.8
             + vec3(0.35, 0.55, 0.9) * rim * 0.4;

  outColor = vec4(pow(color, vec3(1.0 / 2.2)), 1.0);  // 伽马编码后输出

// ---------- 球体几何：UV Sphere ----------
function createSphereGeometry(radius = 1, segments = 64, rings = 40) {
  const positions = [], normals = [], uvs = [], indices = [];

  for (let y = 0; y <= rings; y++) {
    const v = y / rings;                 // 0 → 1，从北极到南极
    const phi = v * Math.PI;
    const sinPhi = Math.sin(phi), cosPhi = Math.cos(phi);

    for (let x = 0; x <= segments; x++) {
      const u = x / segments;            // 0 → 1，绕一圈
      const theta = u * Math.PI * 2;
      const sinTheta = Math.sin(theta), cosTheta = Math.cos(theta);

      // 单位球面上的点方向就是法线方向
      const nx = sinPhi * cosTheta;
      const ny = cosPhi;
      const nz = sinPhi * sinTheta;

      positions.push(nx * radius, ny * radius, nz * radius);
      normals.push(nx, ny, nz);
      uvs.push(u, 1 - v);                // v 翻转，让纹理正立
    }
  }

  const stride = segments + 1;
  for (let y = 0; y < rings; y++) {
    for (let x = 0; x < segments; x++) {
      const a = y * stride + x;
      const b = a + stride;
      indices.push(a, a + 1, b);         // 逆时针绕序，法线朝外
      indices.push(a + 1, b + 1, b);
    }
  }
  return { positions, normals, uvs, indices };
}

class OrbitCamera {
  constructor(element, target = [0, 0, 0]) {
    this.element = element;
    this.target = target;
    this.distance = 5;
    this.theta = 0.6;            // 水平角，绕 Y 轴
    this.phi = Math.PI / 2.4;    // 极角，0 = 正上方
    this.dragging = false;
    this.lastX = 0;
    this.lastY = 0;
    this.bind();
  }

  bind() {
    const el = this.element;

    el.addEventListener('pointerdown', (e) => {
      this.dragging = true;
      this.lastX = e.clientX;
      this.lastY = e.clientY;
      el.setPointerCapture(e.pointerId);      // 拖出画布仍能收到事件
    });

    el.addEventListener('pointermove', (e) => {
      if (!this.dragging) return;
      const dx = e.clientX - this.lastX;
      const dy = e.clientY - this.lastY;
      this.lastX = e.clientX;
      this.lastY = e.clientY;

      this.theta -= dx * 0.008;
      this.phi -= dy * 0.008;

      const eps = 0.02;                       // 限制极角，避免在极点处翻转
      this.phi = Math.max(eps, Math.min(Math.PI - eps, this.phi));
    });

    el.addEventListener('pointerup', (e) => {
      this.dragging = false;
      el.releasePointerCapture(e.pointerId);
    });

    el.addEventListener('wheel', (e) => {
      e.preventDefault();
      this.distance *= Math.exp(e.deltaY * 0.001);   // 指数缩放，手感均匀
      this.distance = Math.max(2.0, Math.min(24, this.distance));
    }, { passive: false });
  }

  /** 球坐标 → 世界坐标 */
  getPosition() {
    const sinPhi = Math.sin(this.phi);
    return [
      this.target[0] + this.distance * sinPhi * Math.sin(this.theta),
      this.target[1] + this.distance * Math.cos(this.phi),
      this.target[2] + this.distance * sinPhi * Math.cos(this.theta),
    ];
  }

  /** 更新视图矩阵，并返回相机世界坐标（渲染循环里还要用它算高光与边缘光） */
  update(viewMatrix) {
    const pos = this.getPosition();
    mat4.lookAt(viewMatrix, pos, this.target, [0, 1, 0]);
    return pos;
  }
}

L4 · 离屏渲染与后处理链

目标：用帧缓冲把场景渲到纹理，再走两遍后处理合成到屏幕。掌握这一关，阴影贴图、泛光、景深、拾取就都只是"换个着色器"的事。

这一关在做什么：把"画到屏幕"改成"先画到一张纹理"。前三个案例都是直接渲染到屏幕，L4 第一次让渲染结果经过二次加工。这是渲染管线里一个重要的转折点。

为什么非要多这一步：有些效果根本无法在一次绘制里完成。比如模糊，某个像素的最终颜色取决于它周围的像素，但你画这个像素时，周围的还没画完，读不到。再比如暗角、色差、色调映射，都需要"整幅画面都画完之后再统一处理一遍"。

还有一个更根本的限制：屏幕是只写不读的。你不能一边往屏幕上画、一边读取屏幕像素，那会形成反馈循环。所以必须有一个中间目标存下第一遍的结果。

打个比方：L1 到 L3 是直接拿画笔在纸上画；L4 是先用相机拍一张照片（Pass 1），再用修图软件给照片套滤镜、加暗角（Pass 2），最后导出。滤镜作用于整张照片，而不是画上去的每一笔，这个差别就是后处理的本质。

核心机制是帧缓冲对象（FBO）：平时 GPU 画到"默认帧缓冲"（屏幕），你可以自己造一个帧缓冲，让它画到一张自定义纹理上。这张纹理之后就能像普通贴图一样被采样。L4 里 createRenderTarget 挂两个附件，它们的选型有讲究：

  • 颜色附件用纹理：因为 Pass 2 要采样它，必须是纹理。内部格式 RGBA8 表示每像素 4 字节。
  • 深度附件用 renderbuffer：Pass 1 画球体需要深度测试，否则球体前后会错乱；但深度数据不需要被采样，用 renderbuffer 更省内存。

记住这条判断依据：会被采样的用纹理，只当缓冲区用的用 renderbuffer。

阶段做什么状态要求
Pass 1 场景到离屏绑定 FBO → 视口设为纹理尺寸 → 清颜色与深度 → 画球体开深度测试（球体要正确遮挡）
Pass 2 后处理到屏幕绑定屏幕 → 视口设为画布尺寸 → 画一个全屏三角形 → 采样 Pass 1 的纹理加工后输出关深度测试（全屏平面不需要深度，开着可能被整块丢弃导致黑屏）

全屏三角形的技巧：三个顶点 (-1,-1)、(3,-1)、(-1,3) 直接写在裁剪空间。后两个坐标故意超出 [-1,1]，超出部分会被 GPU 自动裁掉，剩下的正好铺满屏幕。不用两个三角形拼四边形，是因为那样多一次图元装配，还可能出现接缝，一个大三角形更省也更干净。

后处理着色器做三件事：色差（RGB 三通道按略微不同的方向偏移采样，模拟镜头色散）、暗角（按到中心的距离衰减，越靠边越暗）、灰度（按感知亮度权重压灰再混回，降低饱和度）。三者都不改变几何，只改颜色。

为什么离屏纹理的 wrap 必须用 CLAMP_TO_EDGE：后处理采样时坐标可能略微超出 [0,1]，若用 REPEAT 会绕回对面取色，画面边缘就会出现对面颜色的条纹。这是本关最容易踩的坑。

这一关真正的收获是"渲染到纹理"这个能力，后处理只是它最直观的应用。往下延伸，阴影贴图（从光源视角渲染深度）、平面反射（镜像相机渲染一张图贴到地面）、拾取（渲染 ID 颜色）、GPGPU（用片元着色器做通用计算），全都是同一个套路。

与 L3 的关系：L4 = L3 + 一层离屏处理。球体几何、光照着色器、轨道相机完全不用改，改动只有三处：新增离屏目标、新增后处理着色器与全屏三角形、把渲染循环改成两个 Pass。下面按这三处给出完整代码。

function createRenderTarget(gl, width, height) {
  const framebuffer = gl.createFramebuffer();
  gl.bindFramebuffer(gl.FRAMEBUFFER, framebuffer);

  const colorTexture = gl.createTexture();
  gl.bindTexture(gl.TEXTURE_2D, colorTexture);
  gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA8, width, height, 0, gl.RGBA, gl.UNSIGNED_BYTE, null);
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.LINEAR);
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.LINEAR);
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_WRAP_S, gl.CLAMP_TO_EDGE);   // 后处理必须用 CLAMP，
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_WRAP_T, gl.CLAMP_TO_EDGE);   // 否则边缘会采到对面的像素
  gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT0, gl.TEXTURE_2D, colorTexture, 0);

  const depthBuffer = gl.createRenderbuffer();
  gl.bindRenderbuffer(gl.RENDERBUFFER, depthBuffer);
  gl.renderbufferStorage(gl.RENDERBUFFER, gl.DEPTH_COMPONENT24, width, height);
  gl.framebufferRenderbuffer(gl.FRAMEBUFFER, gl.DEPTH_ATTACHMENT, gl.RENDERBUFFER, depthBuffer);

  if (gl.checkFramebufferStatus(gl.FRAMEBUFFER) !== gl.FRAMEBUFFER_COMPLETE) {
    throw new Error('帧缓冲不完整');
  }
  gl.bindFramebuffer(gl.FRAMEBUFFER, null);
  return { framebuffer, colorTexture, depthBuffer, width, height };
}

in vec3 aPosition;        // 基础形状顶点（例如一个平面四边形）
in vec3 aOffset;          // 每实例：世界位置

in float aPhase;          // 每实例：动画相位，错开运动

uniform float uTime;
uniform float uPointSize;

out vec4 vColor;
out vec2 vLocal;

void main() {
  // 每个粒子独立漂浮：用相位错开，避免整体同步摆动
  vec3 offset = aOffset;
  offset.y += sin(uTime * 1.4 + aPhase) * 0.35;
  offset.x += cos(uTime * 0.7 + aPhase * 1.7) * 0.2;

  vColor = aColor;
  vLocal = aPosition.xy;        // 传给片元画圆形软边
  gl_Position = uViewProjectionMatrix * world;
  gl_PointSize = uPointSize * aScale;
}

#version 300 es
precision highp float;
in vec4 vColor;
in vec2 vLocal;
out vec4 outColor;

void main() {
  // 把方形的点画成圆形，并做边缘渐隐，避免硬边
  float d = length(vLocal);

  if (alpha < 0.01) discard;              // 完全透明直接丢弃，省下混合开销

}

js点击拾取：把鼠标位置换算成粒子索引
// 思路：粒子是点云，用"投影到屏幕后找最近点"最快，
// 不需要颜色拾取的开销。十万个点的距离计算在 JS 里约 1–2 ms，可接受。

function pickParticle(clientX, clientY, particles, viewProjection, canvas) {
  const rect = canvas.getBoundingClientRect();
  const px = clientX - rect.left;
  const py = clientY - rect.top;

  let bestIndex = -1;
  let bestDistSq = Infinity;
  const threshold = 24;              // 屏幕空间命中半径（像素）

  const m = viewProjection;
  for (let i = 0; i < particles.length; i++) {
    const p = particles[i];
    // 手动做 mat4 * vec4（比逐点构造数组快）
    const cx = m[0] * p.x + m[4] * p.y + m[8]  * p.z + m[12];
    const cy = m[1] * p.x + m[5] * p.y + m[9]  * p.z + m[13];
    const cw = m[3] * p.x + m[7] * p.y + m[11] * p.z + m[15];
    if (cw <= 0) continue;                        // 在相机背后，跳过

    // NDC → 屏幕像素
    const sx = (cx / cw * 0.5 + 0.5) * canvas.width;
    const sy = (1 - (cy / cw * 0.5 + 0.5)) * canvas.height;

    const dx = sx - px * (canvas.width / rect.width);
    const dy = sy - py * (canvas.height / rect.height);
    const distSq = dx * dx + dy * dy;

    if (distSq < bestDistSq) {
      bestDistSq = distSq;
      bestIndex = i;
    }
  }

  return bestDistSq <= threshold * threshold ? bestIndex : -1;
}

// 每个格子记录可能落入的粒子索引）缩小候选集，把 O(n) 降到接近 O(1)。

这一关的性能心法：十万粒子的关键是"一次 draw call + 全部数据常驻显存 + 动画在顶点着色器里算"。逐粒子在 CPU 更新位置再上传，即使优化到极致也只能跑到几千个。把动画逻辑写进 GLSL 用 uTime 驱动，CPU 每帧只需要更新一个 uniform。

6.1 性能优化清单

瓶颈判断依据优化手段

测量方法

  • 先区分 CPU 还是 GPU 瓶颈：把渲染分辨率降到 1/4，若帧率大幅提升说明是填充率/GPU 瓶颈；若几乎不变说明是 CPU 或 draw call 瓶颈。
  • 浏览器 Performance 面板：录制一段操作，看每帧的脚本耗时与 GPU 耗时分布。
  • 逐项削减法：注释掉一部分绘制，看帧率变化，定位到具体是哪个环节贵。
  • EXT_disjoint_timer_query_webgl2：能拿到 GPU 侧的真实耗时（部分浏览器因安全策略已限制，需实测）。

维度WebGLWebGPU

迁移策略：把渲染逻辑封装成薄薄一层抽象（渲染器接口 + 资源句柄），让上层业务不直接依赖 GL 调用。实测中真正耗时的不是重写着色器，而是资源生命周期的管理与状态设置的语义差异。

6.4 与 three.js 的分工

  • 用原生 WebGL 做：性能极端敏感的自定义渲染、包体积要求极小（几百 KB 也是负担）、需要 GPGPU、作为学习与面试的知识底座。
  • 用 three.js 做：绝大多数三维业务（模型展示、数字孪生、数据可视化、产品配置器）。它把矩阵、光照、材质、加载器、后处理全部封装好了。
  • 两者结合的进阶路径：three.js 搭骨架，用 ShaderMaterial 或 onBeforeCompile 注入自定义 GLSL 实现特殊效果。这是实际项目里最常见的深水区，前提是你能读懂原生 WebGL。

基础题

W1WebGL 是什么？它和 Canvas 2D 的本质区别在哪？基础

结论：Canvas 2D 是 CPU 光栅化的绘图 API（你给我路径，我帮你画）；WebGL 是把 GPU 渲染管线暴露给 JS 的底层接口（你给我顶点数据和着色器，我按你的程序在 GPU 上并行算出像素）。

三点实质差异

  • 执行位置：Canvas 2D 在 CPU 上逐像素/逐路径计算；WebGL 的顶点与片元着色器在 GPU 上大规模并行执行。
  • 编程模型：Canvas 2D 是命令式的即时绘制；WebGL 是"准备数据 + 写两个着色器 + 提交绘制"的管线模型，状态机式管理。
  • 能力边界：Canvas 2D 适合二维图表、矢量绘制；WebGL 适合三维场景、海量图元、自定义着色效果，也可反过来做通用计算。

加分点

补一句"Canvas 2D 在部分浏览器内部也是用 GPU 加速的（如 Skia 后端），但那层加速对你不可见也不可编程；WebGL 的价值在于把管线本身交给你控制"。

W2完整说一遍渲染管线的阶段。基础

顶点数据（VBO + EBO）→ 顶点着色器 → 图元装配 → 裁剪与透视除法 → 视口变换 → 光栅化 → 片元着色器 → 逐片元操作（剪裁/模板/深度测试 → 混合）→ 写入帧缓冲。

每个阶段的职责

  • 顶点着色器：每顶点一次，算 gl_Position 并输出插值数据，不能访问其他顶点。
  • 图元装配与裁剪：按 mode 组装点/线/三角形，裁掉视锥外的部分。
  • 光栅化：三角形转成片元（候选像素），并插值 varying。
  • 片元着色器：每片元一次，算出最终颜色。
  • 逐片元操作：各种测试与混合，决定像素最终值。

引出的关键判断

片元着色器的执行次数远多于顶点着色器（一个覆盖十万像素的三角形只有 3 个顶点），所以性能优化的重心通常在片元阶段（填充率、overdraw），而不是顶点阶段。

W3attribute、uniform、varying 三者有什么区别？基础
类型WebGL 2 写法更新频率可在哪用

Uniformuniform每次 draw call 内不变两者都可以

attribute（顶点属性）、varying（插值变量），uniform 名字不变。GLSL ES 3.00 统一成 in/out，片元输出也从内置的 gl_FragColor 改成自定义 out 变量。

实践提醒

数据量大的参数（如每个物体的颜色）不该用 uniform 逐个传，那会变成多次 draw call；放进顶点属性配合实例化才能一次画完。

W4gl_Position 为什么是四维的？w 分量起什么作用？基础

结论：四维是齐次坐标的表示，w 是透视除法的载体。GPU 会在光栅化前把 (x, y, z, w) 各分量除以 w，得到 NDC 坐标，这就是"近大远小"的数学实现。

两个推论

  • 方向向量写 (x, y, z, 0)，除以 w 时不受影响，也不会被平移——这正是"方向不该被平移"的表达。
  • 透视投影矩阵的第四行是 (0, 0, -1, 0)，把 z 取反写进 w；相机前方 z 为负，于是远处得到较大的 w，除以它之后被压缩。

常见错误

在片元着色器里直接用 gl_FragCoord 做世界坐标计算时忘记它已经是屏幕空间；或者手动构造 vec4 时把 w 写成 0 导致顶点被丢到无穷远。

W5VAO、VBO、EBO 分别解决什么问题？基础
  • VBO（ARRAY_BUFFER）：把顶点数据放到显存，避免每次绘制都从 CPU 传数据。
  • EBO（ELEMENT_ARRAY_BUFFER）：用索引复用顶点。一个立方体 8 顶点 + 36 索引，比 36 个顶点省 78% 的数据量。
  • VAO：把"哪个 VBO 的哪一段喂给哪个 attribute"这套配置整体保存。没有它，每次切换模型都要重复调用十几次 vertexAttribPointer + enableVertexAttribArray。

WebGL 2 的关键改进

VAO 在 WebGL 2 里是核心特性；WebGL 1 需要 OES_vertex_array_object 扩展，且不同设备支持情况不一，这也是推荐直接用 WebGL 2 的原因之一。

易错点

VAO 会记录 ELEMENT_ARRAY_BUFFER 的绑定（索引缓冲），但不记录 ARRAY_BUFFER 的绑定（不记录是哪个 VBO，只记录属性指针指向的数据范围）。所以切换 VAO 后可以直接 bufferData 到 ARRAY_BUFFER 而不影响已配置的 VAO。

W6纹理过滤与 mipmap 是做什么的？基础

过滤方式

  • NEAREST：取最近像素，硬边，像素风。
  • LINEAR：双线性插值，平滑。
  • LINEAR_MIPMAP_LINEAR：三线性，在 mip 层级之间也插值，缩小场景的标准选择。

mipmap 解决两个问题

  1. 摩尔纹/闪烁：当一个 texel 覆盖多个像素时，只采样一个 texel 会产生严重的走样。mipmap 用预生成的缩小版本代替，本质是一种空间域抗锯齿。
  2. 纹理缓存命中率：远景用小图能让更多采样落在缓存内，提升带宽效率。

代价与注意

显存增加约 33%（1/4 + 1/16 + … 的等比级数）。另外使用 mipmap 过滤必须调用 generateMipmap，否则纹理被判定为不完整，采样结果全黑且不报错——这是最经典的坑之一。

W7深度测试的作用是什么？为什么透明物体必须排序？基础

深度测试

每个片元带一个深度值，与深度缓冲中已有值比较（默认 LESS），通过才写入。它解决"谁挡住谁"的问题，让绘制顺序不影响结果。前提是清除时包含 DEPTH_BUFFER_BIT，且上下文创建时开启 depth。

透明为什么必须排序

正确的不透明渲染依赖深度写入；而半透明的正确结果是"所有层按前后顺序叠加"，本身与绘制顺序有关。若透明物体既参与深度测试又写入深度，先画的透明片元会挡住后面本该透出来的物体，出现"透明物体后面的东西消失"。标准做法：

  1. 先渲染所有不透明物体（写深度）。
  2. 再渲染透明物体：gl.depthMask(false) 关闭深度写入，按到相机距离从远到近排序绘制。
  3. 结束后恢复 gl.depthMask(true)。

注意

排序基于物体中心，互相穿插的透明物体会出现排序错误，这是实时渲染里的经典难题，通常靠拆分网格或使用 OIT（顺序无关透明）方案缓解。

W9解释一下 MVP 三个矩阵，各自从哪个空间变到哪个空间？进阶
  • M（模型矩阵）：局部空间 → 世界空间。由平移、旋转、缩放组合而成，描述"这个物体放在场景的什么位置、什么朝向、多大"。
  • V（视图矩阵）：世界空间 → 相机空间。本质是相机变换的逆：把相机移到原点、朝向 -Z。常用 lookAt(eye, center, up) 构造。
  • P（投影矩阵）：相机空间 → 裁剪空间。透视投影把 -z 写进 w，配合 GPU 的透视除法实现近大远小；正交投影不做这个压缩。

组合顺序

顶点着色器里写 P * V * M * vec4(pos, 1.0)，矩阵乘法从右往左作用于顶点。CPU 侧可以预先算好 VP，减少 uniform 与运算量。

加分点

主动指出"WebGL 的 NDC 深度范围是 [-1, 1]，WebGPU/D3D 是 [0, 1]，所以两者的投影矩阵最后一行不同"。这是能体现迁移经验的一句话。

W10法线为什么不能直接用模型矩阵变换？在什么情况下能凑合？进阶

结论：法线要用法线矩阵，即模型矩阵左上 3×3 的逆转置（inverse transpose）。

为什么

法线的定义是"垂直于表面"。对表面做非等比缩放（如 scale(1, 2, 1)）后，原来的垂直关系被破坏，若仍用模型矩阵变换法线，得到的方向会偏离真实表面法线，表现为光照方向错乱、高光位置不准。

推导思路

切线与法线在变换后仍应保持垂直：dot(M·T, N') = 0 且 dot(T, N) = 0，可推出 N' = (M⁻¹)ᵀ · N。

什么情况下能凑合

只有旋转与等比缩放时，法线矩阵在方向上等价于模型矩阵的 3×3 部分，这也是很多 demo 直接写 mat3(uModelMatrix) 也"看起来没问题"的原因。一旦出现非等比缩放就会露馅。

W11帧缓冲（FBO）能用来做什么？进阶

结论：FBO 让渲染目标从默认帧缓冲（屏幕）改成自定义的纹理或 renderbuffer，是实现一切"二次利用渲染结果"技术的基础。

典型场景

  • 后处理：场景渲到纹理，再用全屏着色器做模糊、色调映射、泛光、色差。
  • 阴影贴图：从光源视角渲染深度到纹理，主渲染时比较深度判断遮挡。
  • 平面反射：用镜像相机渲染场景到纹理，再贴到反射面上。
  • 拾取：渲染 ID 颜色到离屏纹理，点击时读像素反查对象。
  • 延迟渲染：MRT 把位置、法线、材质参数写进多张纹理，光照阶段再统一计算。
  • GPGPU：用片元着色器做通用计算，结果写入浮点纹理。

实现要点

必须用 checkFramebufferStatus 校验完整性；颜色附件用纹理（要采样），深度附件用 renderbuffer（不采样，更省内存）；纹理的 wrap 必须是 CLAMP_TO_EDGE，否则后处理采样时边缘会串到对面。

W12说说阴影贴图的原理，以及如何缓解阴影失真。进阶

两步流程

  1. 把相机换成光源视角（平行光用正交投影，点光源用透视投影），渲染场景深度到一张纹理（阴影贴图）。
  2. 正常渲染时，把当前片元的世界坐标变换到光源空间，取其深度与阴影贴图记录的最近深度比较：更远说明被遮挡，处于阴影中。

三类典型失真与对策

失真现象对策
Shadow acne（自阴影条纹）表面出现条纹状噪点加 depth bias / normal offset；调整光源投影的近远平面
Peter-panning（阴影脱离物体）阴影与物体之间出现缝隙bias 不要过大；改用 normal offset 代替深度偏移
锯齿与硬边阴影边缘呈阶梯状PCF（多次采样取平均）、提高阴影贴图分辨率

进阶方案

大场景用级联阴影贴图（CSM）按距离分层，近处用高分辨率；软阴影用 PCSS 按遮挡距离动态决定模糊半径。

W13混合（Blending）的公式是什么？预乘 alpha 有什么好处？进阶

通用公式

结果 = 源颜色 × srcFactor + 目标颜色 × dstFactor，通过 blendFunc(srcFactor, dstFactor) 配置。

模式配置场景
标准 alphaSRC_ALPHA, ONE_MINUS_SRC_ALPHA常规半透明
加性SRC_ALPHA, ONE发光、粒子、光晕
预乘 alphaONE, ONE_MINUS_SRC_ALPHA纹理已预乘
相乘DST_COLOR, ZERO阴影投射、正片叠底

预乘 alpha 的好处

  • 混合公式更简洁（ONE 代替 SRC_ALPHA），少一次乘法。
  • 解决"边缘发黑"：常规 alpha 纹理在插值后，透明像素的颜色会渗进边缘；预乘后 rgb 已按 alpha 加权，插值结果正确。
  • 多次叠加（如多层半透明 UI）时结果更符合直觉。

实践提醒

纹理是否为预乘决定了该用哪种 blendFunc，两者不匹配会导致画面过亮（重复乘了 alpha）或过暗。这也是 three.js 里 material.premultipliedAlpha 的意义。

W14draw call 为什么是性能瓶颈？有哪些减少手段？进阶

原因：每次 draw call 都要在 CPU 侧做状态校验、参数检查、驱动调用，再通过命令缓冲提交给 GPU。单次开销不大（几十微秒量级），但数量一多就线性累积；同时大量小批次会让 GPU 频繁等待，利用率下降。

七种减少手段

  1. 合批：相同材质的静态几何体合并成一个 BufferGeometry，一次绘制。
  2. 实例化：同一模型画多次，用 drawArraysInstanced + vertexAttribDivisor。
  3. 纹理图集：多张小图合成一张，减少纹理切换与材质种类。
  4. 状态排序：按 program、纹理、混合状态排序绘制顺序，减少状态切换。
  5. 视锥剔除：不画视野外的物体。
  6. 遮挡剔除：大物体挡住的小物体直接跳过。
  7. LOD：远处用低模甚至用一张贴图代替网格。

测量

用 Spector.js 抓一帧，直接看 draw call 数量与状态切换次数。数量超过几百就要考虑合批，超过几千基本必然卡。

W15什么是 Overdraw？怎么优化？进阶

定义：同一个像素在同一帧被片元着色器重复计算多次。比如画了 10 层全屏半透明面板，这个像素就跑了 10 次片元着色器，GPU 做了 10 倍无效功。

判断方法

降低渲染分辨率后帧率大幅提升 → 说明是填充率/overdraw 瓶颈；用浏览器 DevTools 或 GPU 调试工具可以可视化 overdraw 热力图。

优化手段

  • 控制前后顺序：不透明物体从近到远渲染，让 GPU 的早期深度测试提前丢弃被遮挡的片元。
  • 减少半透明面积：粒子、光效、UI 半透明层是 overdraw 的主要来源。
  • 用 alpha test 代替 alpha blend：discard 的片元不参与后续混合，能显著减轻负担（代价是边缘硬）。
  • 减少后处理层数：每多一个全屏 pass 就多一次全屏 overdraw。
  • 移动端降低分辨率：动态分辨率是最高效的兜底手段。
W16sRGB 与线性空间的关系是什么？处理错了会怎样？进阶

结论：图片文件里存的是 sRGB 编码值（人眼友好的非线性），而光照计算必须在线性空间做，计算完再编码回 sRGB 输出。混用会导致画面发灰或过曝。

正确做法

  • 颜色类贴图（漫反射、自发光）→ 内部格式用 SRGB8_ALPHA8，采样时 GPU 自动解码到线性。
  • 数据类贴图（法线、粗糙度、金属度、AO）→ 用普通 RGBA，绝不能做 sRGB 转换，否则数值语义被破坏。
  • 输出前做伽马编码（pow(color, 1/2.2)），或交给浏览器的色彩管理。

常见症状

所有颜色贴图都当线性用 → 画面偏暗偏灰、对比度不足；所有贴图都当 sRGB 用 → 法线贴图方向错误、光照诡异。加性混合（发光）在错误的色彩空间里会明显过曝，因为线性空间下 1+1=2 是真实的两倍亮度，而 sRGB 空间下的叠加会失真。

W17怎么用 WebGL 做通用计算（GPGPU）？进阶

思路

把要计算的数据编码成纹理，用片元着色器当作"并行计算函数"，输出写入浮点纹理，再把结果读回或直接用作下一次渲染的输入。

关键配置

  • 需要 EXT_color_buffer_float 扩展以支持浮点渲染目标。
  • 输入数据用 texelFetch 按整数坐标精确取值，避免过滤引入误差。
  • 用一个覆盖屏幕的三角形让每个像素对应一个计算任务。
  • 乒乓（ping-pong）：两张纹理轮流当作输入与输出，适合迭代算法。

适用与不适用

适合：粒子物理、图像处理（模糊、卷积、直方图）、流体、路径追踪的降噪。不适合：需要复杂分支、原子操作、共享内存的算法——那是 WebGPU 计算着色器的领域。这也是 WebGPU 最实在的升级点之一。

W19十万个粒子，怎么写才能跑满 60fps？进阶

四条硬要求

  1. 一次 draw call：用 drawArraysInstanced 或一个包含十万个点的大缓冲（POINTS 图元），绝不在 JS 里循环调用绘制。
  2. 数据常驻显存：位置、颜色、尺寸一次性上传到 VBO，每帧只更新必要的部分（或干脆不更新）。
  3. 动画在 GPU 算：用 uTime 在顶点着色器里推导位置（噪声、正弦、曲线），CPU 每帧只改一个 uniform。若必须 CPU 计算，用 bufferSubData 局部更新，并考虑放进 Worker。
  4. 减少片元开销：粒子不透明就直接关混合；半透明用加性混合且关闭深度写入；半径外直接 discard。

实测参考

十万个四边形实例（每个 6 顶点）在桌面独显上通常能稳定 60fps；移动端建议控制在 1–2 万。若用 POINTS 图元可到百万级，代价是点大小上限受驱动限制、无法做旋转。

常见错误

每帧 new Float32Array 重建数据、每帧重新创建 buffer、在 JS 里遍历十万个粒子更新数组并整体重传——这三件事加起来能吃掉 20ms 以上。

W20页面打开是黑屏，你怎么排查？原理/场景

按顺序排查，每一步都能砍掉一半可能性

  1. 看控制台：着色器编译错误、链接错误、WebGL 上下文创建失败都会打印。这一步能解决大多数问题。
  2. 确认上下文拿到了：getContext('webgl2') 返回 null 时后续全都不成立。
  3. 把片元输出改成纯色：如果能看到颜色，说明管线通了，问题在顶点数据或矩阵；如果还是黑，说明绘制根本没发生或全被裁掉。
  4. 把 gl_Position 写成 vec4(aPosition, 1.0)：能看到东西就说明顶点数据正确，问题出在矩阵链。
  5. 检查清屏与视口：clearColor 与背景同色会误判为"什么都没画"；viewport 没设或设错（如还在用旧尺寸）会让画面缩在一角。
  6. 检查绘制调用：count 是否为 0、索引起点/数量是否正确、VAO 是否绑定、drawElements 的 type 与索引数据类型是否一致。
  7. 关掉所有可选状态：深度测试、背面剔除、混合、纹理采样逐个关闭，看何时恢复正常。

加分点

强调"用二分法排除"而不是"逐个猜"：先确认是"没画"还是"画了看不见"，再确认是"顶点问题"还是"片元问题"，路径会短很多。

迁移最需要注意的三点

  1. 着色器要重写：GLSL → WGSL 不是语法替换，uniform 变成绑定组内的资源，纹理与采样器分离，全局变量（如 gl_Position）变成结构体字段。
  2. 投影矩阵要改：深度范围从 [-1,1] 变成 [0,1]，同一个角度参数在不同约定下会有差异，容易算错。
  3. 状态管理重构：WebGL 里"设一次就一直生效"的写法在 WebGPU 里不存在，所有状态打包进 Pipeline，需要在架构层面重新组织。

务实建议

把渲染逻辑收敛到一层薄抽象（渲染器接口 + 资源句柄），WebGL 与 WebGPU 各实现一份，上层业务不改。three.js 的 three/webgpu 入口就是这条路线的工业化版本。

W22什么时候该用原生 WebGL，什么时候用 three.js？原理/场景

用 three.js 的信号

  • 需求是"展示一个三维场景"：模型查看、产品配置、数字孪生、数据可视化、三维地图。
  • 团队没有图形背景，交付周期紧。
  • 需要加载 glTF、需要阴影、需要后处理、需要 PBR 材质——这些在 three.js 里都是几行代码。

用原生 WebGL 的信号

  • 包体积是硬约束（three.js 压缩后仍有数百 KB）。
  • 需要 GPGPU 或完全自定义的渲染管线，库的抽象反而成为阻碍。
  • 只画几个三角形/线框，引入整个库不划算。

最常见的形态其实是两者结合

three.js 搭骨架 + 自定义着色器做特殊效果（ShaderMaterial、onBeforeCompile）。这时你面对的是"库的渲染流程 + 自己的 GLSL"，读不懂原生 WebGL 就只能照抄示例、无法调试。

面试里的加分表述

"选型不是非此即彼。我的判断标准是：能不能用库的默认能力覆盖 80% 的需求。能就用库；剩下 20% 用自定义着色器补。真正需要从零手写渲染器的情况很少。"

W23用户反馈"在某些手机上特别卡"，你怎么定位与优化？原理/场景

先分类：是"所有中低端机都卡"还是"特定机型卡"

  • 所有中低端机都卡 → 渲染负载超出移动 GPU 能力，做整体降级。
  • 特定机型卡 → 设备相关：驱动 bug、精度退化、纹理尺寸上限、扩展缺失、热降频。

移动端的五个优化优先级

  1. 限制 DPR：手机上把 devicePixelRatio 限制到 1.5–2，或直接用动态分辨率（帧率低于阈值时降到 0.7 倍渲染）。
  2. 砍 overdraw：移动 GPU 是 TBDR 架构，带宽极其宝贵；半透明粒子与多层后处理是重灾区。
  3. 压缩纹理：用 KTX2/Basis，显存占用降到 1/4–1/8，同时加快加载。
  4. 降低精度诉求：片元着色器默认 mediump，只在必要时用 highp；避免在片元里做复杂数学。
  5. 减少状态切换与 draw call：移动端驱动开销比桌面更大，合批收益更明显。

排查手段

用 WebGL Report 收集设备能力信息；加一个"性能埋点"上报首帧耗时与平均帧率，按机型聚合——只看自己那台机器是查不出来的。

W24如果让你设计一个三维数据可视化的渲染架构，你会怎么分层？原理/场景

四层结构

  1. 数据层：原始业务数据（点位、轨迹、指标）→ 归一化与聚合，决定"画什么"。
  2. 几何层：把数据映射成几何体（点云、曲线、柱体、面片），负责坐标变换与实例化数据的准备，输出可直接上传 GPU 的 TypedArray。
  3. 渲染层：着色器与状态管理。每个可视化类型对应一个 program；统一处理相机、光照、后处理链。
  4. 交互层：拾取（射线或颜色）、相机控制、hover 高亮、点击弹窗，与业务事件对接。

三条设计原则

  • 数据变化与几何重建解耦：数据更新只改 VBO 的局部内容（bufferSubData），不要重建整个几何体。
  • 一个 program 尽量覆盖一类可视化：靠 uniform 与顶点属性区分，而不是给每种样式写一个着色器。
  • 交互与渲染分离：拾取不在渲染循环里做，hover 高亮用 uniform 控制而不是改几何。

规模上去之后的处理

数据超过几十万点时，用分级聚合（按相机距离切换细节）、分块加载、以及把动画与位置计算挪进顶点着色器。这也是 three.js 里 InstancedMesh + Points 的常见组合。

9收官自检与延伸

能力自检表

  • 能完整画出渲染管线，说清顶点与片元两个着色器的输入输出与限制。
  • 能解释 gl_Position 的 w 分量为什么能实现透视。
  • 能默写 MVP 的组装顺序，并说清每个矩阵对应的空间转换。
  • 能解释 VAO 保存了什么、不保存什么。
  • 能说清深度测试与混合的执行顺序，以及透明物体为什么要排序并关闭深度写入。
  • 能独立用 FBO 实现渲染到纹理，并用全屏三角形做后处理。
  • 能写出实例化渲染的完整代码（含 vertexAttribDivisor）。
  • 能定位黑屏、纹理全黑、深度错乱这三类典型故障。

与 Three.js 的衔接

学完这份手册，看 three.js 的源码会发现它做的主要是三件事：把场景图翻译成 draw call、管理着色器与 uniform 赋值、处理资源生命周期。这种"看穿一层"的能力，正是从"会用库"到"能改库"的分水岭。

面试前一句话准备：WebGL 的考察核心是"你能不能说清 GPU 在做什么"。把渲染管线的四段（顶点处理 → 光栅化 → 片元处理 → 逐片元操作）与两次"除以 w"（透视除法）、一次"插值"（varying 传递）串起来讲，基本可以支撑一场 40 分钟的深聊。
